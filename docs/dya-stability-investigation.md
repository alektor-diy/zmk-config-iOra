# DYA対応FWのハング調査

この文書はSatelliteを含む開発版で行った調査の履歴。記載の「今回のビルド」は開発版コミット `2601b40` の構成を指す。公開用DYA安定版はこのスタック見直しを継承し、Satelliteの依存・設定を削除している。公開用生成物の情報は [ビルド記録](dya-studio-build.md) を参照。

## 確認した症状

2026-11-17、ユーザー実機で応答の悪化と完全停止を報告。左右を再起動してから一度もDYA Studioへ接続しなくても発生し、再起動が必要になる。診断ストリーミング中だけの入力停止とは別の問題。

現段階ではCPU使用率や実機のスタック最大使用量、停止時のPC・バックトレースを取得できておらず、原因は確定していない。

## ソース・既存バイナリから分かったこと

- `CONFIG_LOG=n` のため、大量のデバッグログ出力は原因候補から外れる。
- 前版の左FWの静的RAM使用量は136,388 / 262,144バイト。全体容量だけでRAM不足とは判断できない。スレッドごとのスタック不足は別に評価する必要がある。
- 前版の逆アセンブルでは `peripheral_event_work_callback` のフレームが528バイト、`runtime_combo_listener` が320バイト、`split_central_split_run_callback` が312バイト。これらは個別関数の値であり、実行中は呼び出し先やイベント再送による追加消費がある。これだけで実際のオーバーフローを証明したものではない。
- 240バイトのsplit relayデータを有効にすると、通常のsplitイベント・コマンドも共通unionのサイズが大きくなる。Studioを使っていない通常入力でもスタック消費に影響する。
- ZMKの `input_processor_temp_layer.c` はシステムワークキュー上でmutexを保持しながら、空になったactionキューを最大10 ms待つ。センサーのmotion処理もこのワークキューで実行されるため、応答悪化の候補。完全停止の原因としては未確認で、依存ソースへの変更は行っていない。
- 当時のSatelliteのStudio広告との競合はSatellite側の `fix/dya-studio-ble-advertising`（`29bd37c09d1904808e2c2ef81e6c31d3e1f58f34`）で修正し、開発版UF2に取り込んだ。iOra固有の広告回避処理は追加していない。完全停止とこの競合の因果関係は未確認。

## 今回の切り分け変更

| スレッド | 前版 | 今回 |
| --- | ---: | ---: |
| システムワークキュー（左右） | 2048 B | 4096 B |
| input（左右） | 1024 B | 2048 B |
| split中央コマンド送信（左） | 512 B | 1024 B |
| Studio RPC（左） | 4096 B | 6000 B |
| 低優先ワークキュー（左右） | 4096 B | 4096 B |

`CONFIG_STACK_USAGE=y` でコンパイル時の `.su` ファイルを出す。実機上で周期的に計測・出力するプロファイラーは追加していない。機能・キーマップ・コンボ上限・センサー感度・レポート間隔・Satelliteは維持する。

## 今回のビルド結果

- 左右ともコンパイル・リンク・UF2生成に成功。出力はリポジトリ直下の `iOra_L.uf2` と `iOra_R.uf2` に更新した。
- 生成設定で上記のスタック値と既存機能を確認。SPI2無効化とUF2の全ブロック構造も再検証した。
- 左RAMは141,892 / 262,144バイト（54.13%）、右RAMは83,776 / 262,144バイト（31.96%）。
- `.su` は左467ファイル、右399ファイル。左の `handle_list_combos` は2784バイト、`fire_fully_pressed_combo` は640バイト、`peripheral_event_work_callback` は528バイト、`runtime_combo_listener` は320バイト、`split_central_split_run_callback` は312バイト。RPC一覧処理はStudio接続時の経路であり、未接続時の完全停止を直接説明するものではない。
- 使用量は個別関数のコンパイル時の値。呼び出し全体の最悪値や実機の最大使用量を計測した結果ではなく、ハング解消は実機確認が必要。

## 実機で必要な比較

1. 左右両方を更新・再起動し、DYA Studioに一度も接続せず通常入力と両ボールを使用する。
2. 前版の完全停止と応答遅延が再発するかを確認する。
3. 改善してもスタック不足が確定したとは扱わない。再発時は、停止時のログ／フォールト情報の採取、Satelliteなど常時動作機能の個別無効化による比較を次の段階で行う。
